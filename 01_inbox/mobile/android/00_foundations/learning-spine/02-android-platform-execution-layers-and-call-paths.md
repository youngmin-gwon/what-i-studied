## Android 플랫폼 실행 계층과 호출 경로

1 장은 Android 기능을 누가 제공하고 무엇과 함께 업데이트하는지 설명했다. 이제 앱이 그 기능을 호출할 때 코드가 실제로 어디에서 실행되는지 살펴본다.

Android 플랫폼은 흔히 앱에서 하드웨어까지 내려가는 층으로 그려진다. 이 그림은 구성 요소의 위치를 파악하는 데는 유용하지만 모든 호출이 같은 층을 차례대로 통과한다는 뜻은 아니다. 어떤 호출은 앱 프로세스 안에서 끝나고, 어떤 호출은 시스템 서비스까지만 가며, 실제 장치가 필요할 때만 HAL 과 커널 드라이버까지 이어진다.

이 장의 핵심 질문은 다음과 같다.

>이 호출은 현재 어느 프로세스에서 실행되며, 실제 기능 소유자에게 도달하기 위해 어떤 프로세스·플랫폼·기기 구현·커널 경계를 넘는가?

여기서는 프로세스를 서로 분리된 메모리와 실행 경계를 가진 프로그램 단위로 이해하면 충분하다. Binder 내부 자료구조와 스레드 풀, 권한 판정의 세부 순서, HAL 버전 체계는 다루지 않는다. 이 내용은 후속 장과 시스템 내부 정본에서 다룬다.

### 1. API 가 보이는 곳과 코드가 실행되는 곳은 다르다

Android SDK 의 공개 API 는 앱이 사용할 수 있는 호출 형식과 동작 계약을 제공한다. 그러나 SDK 에서 클래스와 메서드를 볼 수 있다는 사실만으로 구현 코드가 앱 APK 안에 있다는 결론을 내릴 수는 없다.

하나의 API 호출에는 다음 위치의 코드가 함께 참여할 수 있다.

| 실행 위치 | 들어갈 수 있는 코드와 상태 | 주된 책임 |
| --- | --- | --- |
| 앱 프로세스 | 앱 코드, 앱에 포함된 라이브러리, 프레임워크 클라이언트 코드, 앱 네이티브 라이브러리 | 앱 상태 관리, 입력 검사와 요청 구성 |
| `system_server` | 여러 관리형 프레임워크 시스템 서비스 | 기기 전체 상태와 여러 앱의 요청·정책 조율 |
| 별도 시스템 프로세스 | 네이티브 서비스와 데몬 | 카메라, 그래픽, 네트워크 같은 독립 하위 시스템 운영 |
| 공급자 구현 영역 | HAL 서비스 또는 라이브러리 | 공통 Android 계약을 기기별 구현에 연결 |
| 커널 | Binder 드라이버, 스케줄러, 메모리·네트워크·장치 드라이버 | 프로세스 격리, IPC 와 장치 접근 중재 |
| 하드웨어 | 센서, 카메라, GNSS, 디스플레이 같은 물리 장치 | 실제 측정, 입출력과 연산 수행 |

이 표는 정적인 위치 지도다. 실제 호출 경로는 필요한 책임만 선택해 통과한다.

예를 들어 `Intent` 객체에 값을 추가하는 코드는 앱 프로세스 안의 객체 상태를 바꾸고 끝날 수 있다. 반면 설치된 패키지 정보를 조회하려면 기기 전체의 패키지 상태를 소유한 시스템 서비스에 요청해야 한다. 가속도계 데이터를 받으려면 센서 서비스를 거쳐 기기별 센서 구현까지 이어질 수 있다.

따라서 패키지 이름이나 클래스 이름만으로 호출 경계를 단정하면 안 된다.

- `android.*` API 라고 모두 Binder 를 넘는 것은 아니다.
- Jetpack 코드라고 모두 앱 프로세스 안에서 끝나는 것은 아니다.
- 네이티브 코드라고 자동으로 별도 프로세스나 커널에서 실행되는 것은 아니다.
- 하드웨어 기능 API 라고 매 호출이 실제 장치까지 내려가는 것은 아니다.

### 2. 호출 경로는 세 유형으로 나눌 수 있다

낯선 API 를 처음 볼 때는 세 가지 기본 유형 중 어디에 가까운지 확인한다.

#### 앱 프로세스 안에서 끝나는 호출

`앱 코드 → 앱 객체 또는 앱에 포함된 라이브러리 → 결과`

함수와 상태가 같은 프로세스에 있으면 일반적인 로컬 호출이다. 인수와 결과를 다른 프로세스로 전달할 필요가 없고, 호출자는 같은 주소 공간의 구현을 직접 실행한다.

다만 라이브러리의 출처가 실행 위치를 완전히 결정하지는 않는다. Jetpack 의 어떤 메서드는 로컬 상태만 다루지만 WorkManager 처럼 내부에서 플랫폼 스케줄러나 시스템 서비스를 사용할 수도 있다. 실제 메서드의 책임을 확인해야 한다.

#### 시스템 서비스에서 끝나는 호출

`앱 → 앱 쪽 관리 객체 → Binder → 시스템 서비스 → 응답`

여러 앱이 공유하는 기기 상태나 플랫폼 정책은 한 앱 프로세스가 소유할 수 없다. 이때 앱 쪽 객체는 요청을 만들고, 다른 프로세스의 시스템 서비스가 실제 상태를 조회하거나 변경한다.

설치 패키지 조회가 대표적이다. 앱은 `PackageManager` 진입 객체를 사용하지만 설치 상태와 사용자별 패키지 정보는 플랫폼 서비스가 소유한다. 이 요청은 서비스 상태에서 답할 수 있으므로 HAL 이나 물리 하드웨어까지 내려갈 이유가 없다.

#### 하드웨어 기능까지 이어질 수 있는 호출

`앱 → 시스템·네이티브 서비스 → 필요 시 HAL → 커널 드라이버 → 하드웨어`

센서, 카메라, 오디오처럼 물리 장치가 필요한 기능은 더 아래의 구현 경계를 사용할 수 있다. 그래도 모든 요청이 끝까지 내려가는 것은 아니다. 입력 오류, 기능 부재, 정책 거절, 이미 확보한 상태나 여러 앱의 요청 통합 때문에 더 위에서 끝날 수 있다.

| 구분 질문 | 로컬 호출 | 시스템 서비스 호출 | 하드웨어 기능 호출 |
| --- | --- | --- | --- |
| 다른 프로세스 상태가 필요한가? | 보통 아니다 | 그렇다 | 그렇다 |
| Binder 가 반드시 필요한가? | 아니다 | 흔하지만 API 별 확인 필요 | 한 개 이상의 IPC 경계가 있을 수 있다 |
| HAL 이 필요한가? | 아니다 | 보통 아니다 | 실제 기기 구현이 필요할 때 등장한다 |
| 커널의 역할 | 현재 프로세스 실행 기반 | IPC 중재 | IPC 와 장치 드라이버 모두 관여할 수 있다 |
| 결과 형태 | 로컬 반환·상태 변경 | 동기 응답 또는 콜백 | 콜백, 이벤트 통로, 공유 버퍼 등 다양하다 |

### 3. 관리 객체와 Binder 는 앱과 서비스 구현을 연결한다

Android 앱은 `LocationManager`, `SensorManager`, `PackageManager` 처럼 이름에 Manager 가 붙은 관리 객체를 자주 만난다. 이런 객체는 앱이 기능을 사용하는 진입점이다. 그러나 이름만으로 실제 상태 소유자나 프로세스 위치를 알 수는 없다.

관리 객체는 앱 프로세스에서 인수를 검사하고 요청을 구성하거나 로컬 캐시에서 답할 수 있다. 다른 프로세스가 소유한 상태가 필요하면 Android 의 대표적인 프로세스 간 통신(Inter-Process Communication, IPC) 방식인 Binder 를 통해 요청을 위임한다.

`앱의 관리 객체`

→ `[binder ipc](../../01_system_internals/binder-ipc.md) 경계`

→ `원격 시스템 서비스`

→ `응답 또는 콜백`

Binder 는 요청을 대상 프로세스에 전달하고 호출자 UID 같은 식별 정보를 보존한다. 실제 시스템 서비스는 공유 상태를 소유하고 해당 기능의 정책과 동작을 결정한다. 즉, Binder 는 **전달 경계**이고 서비스는 **상태와 정책의 소유자**다.

Android 내부의 `ServiceManager` 는 이름으로 Binder 서비스 접점을 등록하고 찾는 장부 역할을 한다. 앱이 사용하는 `PackageManager` 같은 관리 객체나 앱 `Service` 컴포넌트와는 다른 개념이다. 등록·조회와 Binder 호출의 세부 구현은 [IPC와 프로세스 계약](../../01_system_internals/ipc-and-process/ipc-process-contracts/ipc-process-contracts.md) 에서 다룬다.

#### 결과가 돌아오는 두 단계를 분리한다

원격 결과는 즉시 응답이나 나중의 콜백·이벤트로 프로세스 경계를 돌아올 수 있다. 결과가 앱 프로세스에 도착한 뒤 어느 실행 문맥에서 앱 코드에 전달되는지는 별도 문제다. 일부 API 는 `Executor`, `Handler` 또는 `Looper` 같은 실행 문맥을 앱이 선택하게 한다.

이 장에서는 원격 경계와 앱 내부 전달이 분리된다는 사실까지만 다룬다. 스레드, 대기와 역압력은 6 장에서 설명한다.

### 4. 시스템 서비스 아래의 계층은 서로 다른 책임을 가진다

Android 문서에는 `Service` 라는 단어가 여러 의미로 등장한다. 먼저 이름을 분리해야 한다.

| 이름 | 의미 |
| --- | --- |
| 프레임워크 시스템 서비스 | 기기 전체 상태와 플랫폼 기능을 관리하는 서비스 |
| `system_server` | 여러 관리형 프레임워크 시스템 서비스를 실행하는 핵심 프로세스 |
| Binder `ServiceManager` | 이름으로 Binder 서비스 접점을 등록·조회하는 내부 장부 |
| 네이티브 서비스·데몬 | 별도 또는 플랫폼 프로세스에서 네이티브 코드로 구현된 하위 시스템 서비스 |
| 앱 `Service` 컴포넌트 | 앱이 선언하는 Android 컴포넌트이자 시스템 진입점 |

`system_server` 는 모든 Android 시스템 서비스의 동의어가 아니다. 많은 프레임워크 서비스가 이 프로세스에서 실행되지만 SurfaceFlinger 나 camera service 처럼 별도 네이티브 프로세스에 있는 서비스도 있다. 반대로 네이티브 서비스라는 이름만으로 항상 별도 프로세스라고 단정할 수도 없다.

#### 구현 방식과 실행 경계를 분리한다

네이티브 코드는 구현 언어와 실행 형식을 가리킬 뿐 별도 프로세스나 더 높은 권한을 자동으로 뜻하지 않는다. 앱과 시스템 프로세스 모두 같은 프로세스 안의 네이티브 라이브러리를 호출할 수 있다.

| 용어 | 이 장에서 구분할 의미 |
| --- | --- |
| JNI | 같은 프로세스 안의 Kotlin·Java 관리 코드와 C/C++ 네이티브 코드를 연결하는 호출 경계 |
| NDK | 앱이 허용된 네이티브 API·ABI 를 사용해 네이티브 라이브러리를 만드는 개발 계약 |
| HAL | Android 플랫폼 구성 요소와 기기별 공급자 구현을 분리하는 사용자 공간 계약 |
| 커널 드라이버 | 커널 공간에서 실제 장치 접근을 중재하는 구현 |

이 용어들의 세부 사용법을 외우는 것이 이 장의 목표는 아니다. JNI 는 기본적으로 프로세스 경계가 아니며, HAL 과 커널 드라이버는 같은 계층이 아니라는 점이 핵심이다.

Hardware Abstraction Layer(HAL)는 카메라, 오디오, 센서 같은 하드웨어별 차이를 공통 Android 프레임워크에서 분리한다. HAL 구현의 프로세스 배치는 Android 버전과 기기 구조에 따라 달라질 수 있다.

`프레임워크·시스템 구성 요소`

→ `HAL이라는 사용자 공간 계약`

→ `기기별 공급자 구현`

→ `커널 드라이버`

→ `물리 장치`

일반 앱은 공개 SDK 또는 허용된 NDK 접점을 우회해 HAL·드라이버를 직접 제어하는 구조를 전제로 하면 안 된다. 플랫폼 서비스가 여러 앱의 요청, 정책과 기기 상태를 조율해야 하기 때문이다.

### 5. 센서 등록과 이벤트 반환 경로를 추적한다

가속도계 이벤트를 구독하는 앱을 생각해 보자. 이 사례는 제어 요청이 아래로 내려가고 센서 데이터가 다시 위로 올라오는 방향을 함께 보여준다.

#### 시작 상태

- 앱 프로세스가 실행 중이다.
- 앱은 Android 센서 API 의 `SensorManager` 와 리스너 접점을 사용한다.
- 기기는 요청한 센서 기능을 제공한다.

#### 제어 요청이 내려가는 경로

1. 앱이 원하는 센서, 샘플링 주기와 지연 조건을 담아 리스너 등록을 요청한다.
2. 앱 프로세스의 프레임워크 코드는 요청을 검사하고 센서 서비스에 전달한다.
3. 센서 프레임워크와 서비스는 여러 앱의 요구를 조율하고, 실제 활성화가 필요하면 기기별 Sensors HAL 구현에 요청한다.
4. 기기별 Sensors HAL 구현은 커널 드라이버를 통해 물리 센서의 측정과 장치 입출력에 연결된다.

#### 센서 데이터가 올라오는 경로

`물리 센서`

→ `커널 드라이버`

→ `기기별 Sensors HAL 구현`

→ `센서 프레임워크·서비스`

→ `앱의 리스너`

등록 요청의 응답이 계속 센서 값을 운반하는 것은 아니다. 센서 이벤트는 버전과 기기 구현에 맞는 별도 데이터 통로로 전달될 수 있다. 여기서 중요한 것은 구체적인 전송 방식이 아니라 **제어 요청과 지속 데이터의 경로가 다를 수 있다**는 사실이다.

#### 프레임워크가 중간에서 조율하는 이유

센서 HAL 은 여러 앱 각각이 하드웨어를 독점하도록 설계된 앱 API 가 아니다. 프레임워크는 여러 앱의 요청을 모아 센서 활성 상태와 샘플링 조건을 조정한다. 첫 요청에서 센서를 활성화하고 마지막 요청이 해제되면 불필요한 전력 사용을 막기 위해 비활성화할 수 있다.

따라서 앱이 요청한 조건과 실제 하드웨어 설정을 일대일로 대응시키면 안 된다. 샘플링 주기와 지연 값의 정확한 의미는 해당 API 계약을 따라야 하며, 프레임워크는 여러 앱의 요구를 만족시키는 공통 설정을 사용할 수 있다.

#### 어느 경계에서 실패했는지 분류한다

| 관찰 결과 | 우선 확인할 경계 |
| --- | --- |
| 요청한 센서가 목록에 없다 | 기능 선언, 기기 구현과 HAL |
| 리스너 등록 자체가 성립하지 않는다 | 앱 인수·수명, 프레임워크 진입 계약 |
| 등록은 됐지만 이벤트가 오지 않는다 | 센서 서비스 상태, HAL·드라이버·장치와 이벤트 통로 |
| 일부 기기에서 값의 품질·주기가 다르다 | 프레임워크 조율, 센서 종류와 OEM·공급자 구현 |
| 콜백 이후 UI 가 멈춘다 | 앱 콜백 처리와 실행 스레드, 6 장 영역 |

이 표는 증상만으로 원인을 확정하는 답안이 아니다. 마지막으로 성공한 경계와 처음 실패한 경계를 찾기 위한 조사 시작점이다.

### 6. 낯선 API 의 실행 경로를 분류한다

새 API 나 장애를 만났을 때 다음 순서로 호출 경로를 그린다.

#### 1. 현재 코드는 어디에서 실행되는가?

앱 APK 에 포함된 코드인지, 앱 프로세스에 로드된 프레임워크 클라이언트 코드인지, 다른 실행 환경의 클라이언트인지 확인한다.

#### 2. 같은 프로세스 안에서 답할 수 있는가?

로컬 상태·계산만 필요한지, 기기 전체 또는 다른 앱과 공유하는 상태 소유자가 필요한지 구분한다.

#### 3. 프로세스 경계를 무엇으로 넘는가?

Binder 가 흔한 경로지만 모든 시스템 통신이 Binder 인 것은 아니다. 소켓, 공유 메모리, 파일 서술자와 전용 데이터 통로가 사용될 수도 있다.

#### 4. 실제 서비스는 어느 프로세스에 있는가?

`system_server` 의 프레임워크 서비스인지, 별도 네이티브 서비스·데몬인지, 다른 앱이나 Google 실행 환경인지 확인한다.

#### 5. 요청이 기기별 구현과 물리 장치를 필요로 하는가?

서비스 상태나 캐시에서 끝나는지, HAL 과 커널 드라이버를 거쳐야 하는지 구분한다. 하드웨어 기능이라는 이름만으로 가장 긴 경로를 가정하지 않는다.

#### 6. 결과는 어떤 통로로 돌아오는가?

먼저 결과가 즉시 응답, 콜백 또는 별도 이벤트 통로 중 어떤 방식으로 프로세스 경계를 돌아오는지 확인한다. 그다음 앱 프로세스 안에서 `Executor`, `Handler` 또는 `Looper` 가운데 어떤 실행 문맥으로 전달되는지 구분한다.

#### 7. 마지막으로 성공한 경계는 어디인가?

앱 입력 검사, IPC 전달, 서비스 정책, HAL 응답, 드라이버·장치와 콜백 전달을 나눠 관찰한다. `Android가 실패했다` 가 아니라 다음처럼 문제를 구체화하는 것이 목표다.

>앱의 리스너 등록은 센서 서비스에 도달했지만 해당 기기의 센서 목록에 요청한 기능이 없으므로 HAL 활성화 단계로 진행되지 않았다.

### 반드시 교정해야 할 오해

| 오해 | 교정 |
| --- | --- |
| SDK 에서 보이는 API 구현은 앱 APK 안에 있다. | SDK 는 공개 호출 계약을 제공하며 실제 구현 위치는 API 마다 다르다. |
| 모든 `android.*` 호출은 Binder 를 넘는다. | 앱 프로세스 안에서 끝나는 프레임워크 객체와 메서드도 있다. |
| 모든 시스템 서비스는 `system_server` 에 있다. | 많은 프레임워크 서비스가 있지만 별도 네이티브 서비스와 데몬도 존재한다. |
| Binder 가 권한과 기능 정책을 결정한다. | Binder 는 전달과 호출자 식별을 중재하고 서비스가 기능별 정책을 판정한다. |
| JNI 는 프로세스 간 통신이다. | JNI 는 기본적으로 같은 프로세스 안의 관리 코드·네이티브 코드 경계다. |
| 네이티브 코드는 커널에서 실행되고 권한이 높다. | 네이티브는 구현 방식이며 프로세스 위치와 권한은 별도 조건이다. |
| NDK 와 HAL 은 같은 네이티브 API 다. | NDK 는 앱 네이티브 개발 계약이고 HAL 은 플랫폼과 기기별 구현의 계약이다. |
| HAL 은 커널 드라이버의 다른 이름이다. | HAL 은 사용자 공간 인터페이스이고 드라이버는 커널에서 장치를 중재한다. |
| 하드웨어 API 는 매번 장치까지 내려간다. | 캐시, 정책, 기능 부재와 요청 통합 때문에 더 위에서 끝날 수 있다. |
| 콜백은 항상 메인 스레드에서 실행된다. | 콜백 실행 문맥은 API 계약과 앱이 제공한 실행기에 따라 다르다. |

### 확인 질문

1. SDK 의 공개 API 와 기기에서 실행되는 실제 구현은 어떻게 다른가?
2. 앱 프로세스 안의 호출과 Binder 를 넘는 호출은 어떤 차이가 있는가?
3. 앱의 관리 객체, Binder 와 원격 서비스는 각각 무엇을 맡는가?
4. Binder 와 시스템 서비스는 각각 무엇을 전달하고 결정하는가?
5. `system_server`, 별도 네이티브 서비스와 앱 `Service` 는 왜 같은 개념이 아닌가?
6. 프로세스 경계, 사용자 공간의 기기 구현 경계와 커널 장치 경계는 어떻게 다른가?
7. 설치 패키지 조회가 HAL 까지 내려가지 않아도 되는 이유는 무엇인가?
8. 센서 등록 요청과 센서 데이터는 어떤 방향과 경로로 이동하는가?
9. 모든 하드웨어 기능 호출이 실제 장치까지 내려가지 않는 이유는 무엇인가?
10. 장애가 발생했을 때 마지막으로 성공한 실행 경계를 어떻게 찾을 수 있는가?

### 다음 장으로 이어지는 질문

이 장은 앱 프로세스에서 시작한 호출이 시스템 구현에 도달하는 경로를 설명했다. 그러나 이 호출의 주체인 앱이 어떻게 설치된 패키지가 되고, 플랫폼이 식별하고 신뢰하는 실행 단위가 되는지는 아직 설명하지 않았다.

다음 장에서는 소스와 자원이 다음 경계를 지나 설치 상태가 되는 흐름을 다룬다.

- 소스, 자원, 매니페스트와 의존성은 어떤 빌드 산출물로 바뀌는가?
- AAB 와 APK 는 배포와 설치에서 어떤 역할을 맡는가?
- 서명은 무엇을 증명하고 패키지 이름과 어떻게 다른가?
- PackageInstaller 와 패키지 관리 서비스는 무엇을 검증·등록하는가?
- 설치된 패키지는 사용자별 UID 와 데이터 경계를 어떻게 얻는가?
